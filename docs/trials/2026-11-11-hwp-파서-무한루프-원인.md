# HWP 파서 무한 루프와 PDF MuPDF 경고의 원인

- 날짜: 2026-11-11 / Phase 1 / 관련 파일: `notebooks/01_데이터탐색.ipynb`
- 앞선 기록: `2026-11-11-파일명-정규화와-HWP-파서-멈춤.md` (증상과 NFC 문제). 이 문서는 그 두 가지 파싱 문제의 **원인 분석**이다. 라이브러리는 수정하지 않았다.

## 1. 케빈랩 영상감시 HWP — `hwp-hwpx-parser` 1.0.0 무한 루프

### 증상
- 해당 파일 1건에서 `Reader(...).text` 가 끝나지 않는다 (60초 제한을 넘기고, 100초 이상 CPU 100%).
- `faulthandler.dump_traceback_later` 덤프: `hwp5.py::_extract_hyperlink_texts_from_para` (while 루프) 안.

### 시도한 것
1. `ExtractOptions` 에 하이퍼링크 추출을 끄는 옵션이 있는지 확인 → 없음 (옵션은 표 스타일/구분자/이미지 마커/빈 문단뿐).
2. 문제 구간의 루프를 반복 횟수 상한을 두고 같은 입력으로 재현해 어느 문단에서 멈추는지 확인.
3. 라이브러리 파일은 그대로 두고 메서드만 교체(몽키패치)한 버전으로 같은 파일을 파싱해 우회 가능한지 확인.

### 원인 (파서 버그 + 파일 특이점 둘 다)
- 섹션 0 에 문단 텍스트 레코드(PARA_TEXT)가 2,560개 있고, **그중 정확히 1개**(14번째 문단, 길이 18바이트)가 `0x0003` 컨트롤 문자 + `0x000d`(문단 끝)로 끝난다.
  - HWP 에서 `0x03` 은 "확장 컨트롤" 시작 코드이고 뒤에 14바이트 페이로드가 따라와야 하는데, 이 문단에서는 페이로드가 잘려 있어 남은 바이트가 4개뿐이다 (파일 쪽 특이점).
- 파서 루프는 `if code == 0x03:` 안에서 `if i + 6 <= len(para_data):` 일 때만 `i` 를 전진시킨다. **조건이 거짓이면(꼬리에 짧게 남은 경우) `i` 가 그대로**라 같은 위치를 영원히 다시 읽는다 (`else` 분기 없음, 파서 쪽 버그).
- 다른 95개 HWP 에는 이런 문단이 없어서 문제가 드러나지 않았다.

### 해결(안)
- 우회 가능 여부: 꼬리에서 잘린 `0x03` 이 나오면 그 앞까지만 검사하도록 메서드를 교체해 보니 **0.2초에 완료**, 본문 56,932자, 표 137개를 얻었다 (원시 PARA_TEXT 를 UTF-16 으로 읽어 컨트롤을 뺀 글자 수는 47,423자로, 파서는 표 셀·머리말 등을 더 포함하므로 이상 없음).
- 권장 처리 (Phase 1-2):
  1. 파서는 **파일 단위 프로세스 격리 + 타임아웃**을 기본으로 한다 (실패 시 목록에 남기고 건너뜀).
  2. 이 문서만 구제하려면 `ingest/hwp.py` 안에서 해당 메서드를 경계 검사가 있는 버전으로 교체(몽키패치)하고 단위 테스트를 둔다. 크기가 작고(약 10줄) 영향 범위가 한 메서드로 제한된다.
  3. 라이브러리 이슈 제보/상위 버전 확인은 별도 판단 (수정은 하지 않음).

### 배운 점
- 외부 파서의 "무한 루프"는 대부분 "특정 입력에서 인덱스가 전진하지 않는" 경계 조건 버그다. 100건 중 1건만 걸려도 배치가 멈추므로 타임아웃은 필수다.

## 2. 서울특별시 지도정보 PDF — MuPDF `invalid key in dict` 경고

### 증상
- `MuPDF error: syntax error: invalid key in dict` 가 이 PDF 한 건에서만 출력된다 (stderr, 예외 없음).

### 시도한 것
1. `pymupdf.TOOLS.mupdf_warnings()` 로 경고 발생 시점 추적 → 문서를 열 때는 없고, 쪽을 처리할 때 (텍스트 1쪽 / `find_tables` 45쪽) 나온다. `doc.is_repaired = False`.
2. 모든 xref 객체를 읽어 보니 **xref 367 한 개만** 같은 오류(`code=8: invalid key in dict`)로 읽히지 않는다. 스트림이 아니고, 어떤 객체도 이를 참조하지 않는다(고아 객체). 45쪽의 contents(xref 371)·글꼴·이미지 목록과도 무관.
3. `garbage=4, clean=True` 로 임시 파일(레포 밖)에 다시 저장해 원본과 쪽별 텍스트 길이/표 개수를 비교.

### 원인
- PDF 안에 참조되지 않는 깨진 딕셔너리 객체 1개(xref 367)가 있고, MuPDF 가 읽다가 경고를 낸다. 페이지 내용(텍스트/표)은 이 객체와 연결되지 않는다.

### 해결(안) / 판단
- **무해하다**고 판단한다. 문서는 복구(repair) 없이 열리고 75쪽 모두 텍스트가 추출된다 (합계 119,803자, 표 127개).
- 재저장본과 비교하면 쪽별 글자 수가 1~3자, 표 개수가 ±1~2 씩 달라지는 쪽이 있었지만 경고가 나는 쪽(45)과 무관하고 저장 옵션(deflate 여부)에 따라 달라지는 위치도 달라서, 오류 객체의 영향이 아니라 재저장 때의 스트림 재인코딩/표 탐지 흔들림으로 본다. 원본 PDF 를 그대로 파싱하면 된다.
- 로그 소음은 `pymupdf.TOOLS.mupdf_display_errors(False)` 로 끄고, 필요하면 `mupdf_warnings()` 를 문서별로 로그에 남긴다.

### 배운 점
- "경고가 난다 = 내용이 깨졌다" 가 아니다. 어느 객체/쪽에서 나는지 먼저 좁혀 보고, 내용 비교로 영향을 확인한다.
